# 客户经理兼用户体验验收报告

审查日期：2026-10-07  
对象：当前工作区版本，包括审查开始前已经存在的未提交改动。  
结论：核心能力可以运行，但尚不建议作为无需开发人员陪同的客户版本交付。当前最重要的风险是“界面告诉用户安全，运行状态却不是安全状态”，以及换号后的数据隔离。

本次没有修改产品代码、现用 .env、Prompt 或正式数据库，没有读取私人聊天内容，没有发送真实 QQ 消息，没有调用付费模型。只新增 artifacts 目录下的验收探针和本报告。

## 优先处理顺序

| 顺序 | 编号 | 优先级 | 理由 |
| --- | --- | --- | --- |
| 1 | U01 | P0 | 用户看到 Dry Run 已开启时，发送器仍可能进入真实通道；安全提示不能作为操作依据。 |
| 2 | U02 | P0 | 同一数据库换号后，账号 A 的历史进入账号 B 的模型请求，破坏账号边界。 |
| 3 | U03 | P1 | 重新连接后，界面仍显示人工接管，新的调度器实际上没有接管。 |
| 4 | U05 | P1 | 生成途中关闭主动聊天，候选完成后仍发送，停止控制没有兑现。 |
| 5 | U04、U10、U09 | P1 / P2 | 发送与错误恢复：未发送内容成为历史、模型错误在桌面静默、失败输入不能恢复。 |
| 6 | U06、U07 | P1 | 群聊与图片场景的核心处理不可靠，导致不回复、乱序或额外回复。 |

## 完整问题清单

### U01：返回首页后，Dry Run 显示开启，但发送器仍处于真实模式

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U01；实际工具栏、首页与 QQ 页回调，Fake 控件和 Sender。  
严重程度：P0。  
受影响用户及场景：已经切换过发送模式、再返回首页进入 QQ 的用户。  
前置条件：启动配置 QQ_DRY_RUN=true，已连接；运行中关闭 Dry Run。  
最短复现步骤：关闭 Dry Run并确认 → 返回首页 → 再进入 QQ → 查看 Dry Run → 用合成消息触发发送。  
实际结果：重建工具栏后勾选值为 true，但运行中的发送器 dry_run=false；Fake 真实通道收到 1 次调用。  
预期结果及依据：工具栏提示“开启时只记录候选发送，绝不调用 QQ 发送接口”；返回页面不能悄悄显示成另一种模式。  
用户影响：用户可能误以为处于安全模拟状态，实际上发出不准备公开的文字。  
证据或相关文件位置：[工具栏从启动配置重建](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:340)、[界面切换只修改 Runtime](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:1287)、[发送器运行状态](C:/Users/24028/Documents/chatbot/app/ui/runtime.py:103)。  
建议改进方向：以实际 Runtime 状态作为显示依据；切换页面不重置开关；发送端保留最终安全校验。  
验收标准：任意首页往返、设置保存、重连后，显示与两个 Sender 一致；显示 Dry Run 开启时，Fake 真实发送调用必须为 0。

### U02：同一数据库换 QQ 账号后，旧账号历史进入新账号模型请求

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U02；重建 Dispatcher 和 SessionManager 后仍可复现。  
严重程度：P0。  
受影响用户及场景：同一安装目录、同一数据库切换登录账号；两个账号都与同一 QQ 联系人交流。  
前置条件：账号 A 已有历史；换成账号 B 时不切换数据库。不是两份独立数据库之间串消息。  
最短复现步骤：A 与联系人发合成唯一标记 → 重建聊天 Runtime → B 与同一联系人发新消息 → 捕获 B 的完整模型请求。  
实际结果：B 请求中包含 A 的唯一合成历史标记 ACCOUNT_A_TEST_SECRET。  
预期结果及依据：README 支持换号；用户看到按登录账号区分的会话，应当获得账号隔离。此处隔离要求也基于隐私体验判断。  
用户影响：新账号获得不属于该账号的聊天上下文；可能引用旧账号关系和私人事实。  
证据或相关文件位置：[会话 ID 不含登录账号](C:/Users/24028/Documents/chatbot/app/adapters/onebot.py:65)、[Dispatcher 按 conversation_id 读取](C:/Users/24028/Documents/chatbot/app/core/dispatcher.py:308)、[历史仅按 session_id 查询](C:/Users/24028/Documents/chatbot/app/storage/database.py:175)、[记忆查询亦缺少账号维度](C:/Users/24028/Documents/chatbot/app/memory/repository.py:234)。  
建议改进方向：统一隔离账号下的消息、摘要、记忆、画像和活动生成；为既有数据提供明确归属策略，不能仅修界面显示。  
验收标准：重连、重启、换号后，B 的模型请求不含 A 标记；同一 QQ 联系人在两个账号下独立；同账号原有上下文仍可恢复。

### U03：重新连接后，“人工接管”仍勾选，调度器实际已恢复自动回复

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U03；实际重连、账号激活和会话选择回调。  
严重程度：P1。  
受影响用户及场景：已接管联系人或群会话，又为调整模型或解决连接问题重新连接。  
前置条件：某会话已勾选人工接管；重连后登录同一账号。  
最短复现步骤：接管会话 → 重新连接 → 登录同账号 → 重新选择会话 → 比较勾选值与新调度器状态。  
实际结果：勾选为 true，新调度器的 human_takeover 为 false。  
预期结果及依据：界面承诺“持续接管当前会话”；没有提示接管结束时，不应显示仍在接管而允许自动回复。  
用户影响：人工沟通期间机器人可能再次插话；用户无法依据开关判断谁在负责回复。  
证据或相关文件位置：[重连重建 Runtime 但未同步接管集合](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:205)、[账号激活](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:537)、[勾选来自界面集合](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:779)。  
建议改进方向：将接管状态作为受账号约束的明确状态同步或恢复；如设计成重连清除，必须先明确告知且同步取消勾选。  
验收标准：重连后勾选与调度器一致；持续接管期间模型调用与自动发送为 0；恢复自动后下一条新消息正常回复。

### U04：QQ 发送失败的模型回复被当成“已经说过”

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U04。  
严重程度：P1。  
受影响用户及场景：NapCat 断线、发送动作失败或服务器拒绝发送。  
前置条件：模型生成成功，Fake Sender 在发送时抛错。  
最短复现步骤：发送合成入站消息 → 让 Sender 失败 → 查询历史 → 再投递同一入站事件。  
实际结果：成功发送数为 0，assistant 历史已有回复；重复事件不会重试发送。  
预期结果及依据：README 定义历史为真实聊天记录，并以发送成功为追加回复前提；生成候选不等于已送达。  
用户影响：机器人可能依据对方根本没收到的话继续接话；客户不知道如何补发。  
证据或相关文件位置：[发送前写入 assistant 和安排记忆维护](C:/Users/24028/Documents/chatbot/app/core/dispatcher.py:134)、[之后才调用 Sender](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:846)。  
建议改进方向：区分候选、待发送、已发送、失败；正式上下文只使用符合约定的已发送记录；提供明确重试，不盲目自动重发超时请求。  
验收标准：失败或未发送的候选不伪装成已送达历史；失败状态可见；重试有幂等性；不会重复发送或重复记忆。

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U05；使用正常主动聊天入口，不使用 force 跳过控制。

最短复现步骤：触发一次主动生成 → 模型暂停 → 关闭主动聊天 → 释放模型结果。  
实际结果：proactive_enabled 已为 false，但 Fake Sender 仍收到 1 条消息。  
预期结果及依据：界面描述该开关控制随机主动消息；未发送的候选应遵守当前开关。  
用户影响：客户认为已停止自动化，仍发生不期望的联系。  
证据或相关文件位置：[开关仅改变布尔值](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:212)、[生成后未重新检查开关](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:433)。  
建议改进方向：关闭时取消或失效化在途主动任务；发送前统一检查开关、账号、接管和版本；已经提交的平台动作另说明边界。  
验收标准：在生成、等待或分段发送之间关闭后，尚未提交的主动消息不再进入 Sender。

### U06：群里无关、未 @ 的消息取消了此前被 @ 后的回复

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U06。  
严重程度：P1。  
受影响用户及场景：回复白名单内的活跃群。  
前置条件：成员 A @ 机器人，模型仍在生成；成员 B 发普通消息。  
最短复现步骤：A @ 并提问 → 暂停模型 → B 发无关普通文本 → 观察生成与发送。  
实际结果：A 的回复被取消，发送数为 0；B 没有 @，所以也不触发后续处理。  
预期结果及依据：README 承诺白名单群被 @ 后回复。体验判断：其他成员的无关聊天不应让这条请求悄悄消失。  
用户影响：热闹群里机器人表现为经常不理人，用户只能反复 @。  
证据或相关文件位置：[未 @ 消息仍进入 record_platform](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:948)、[记录时递增版本并取消生成](C:/Users/24028/Documents/chatbot/app/core/dispatcher.py:315)。  
建议改进方向：区分普通群上下文更新和需要使当前请求过期的补充；需要重新生成时保留待回答请求，勿以允许旧回复发送作为修复。  
验收标准：无关 B 消息不导致 A 请求无结果；A 纠正或撤回请求时仍能正确丢弃旧回复；非 @ 消息不独立触发回复。

### U07：图片处理慢时，后发的问题先进入会话，并产生两次回复

问题性质：功能 Bug。  
证据状态：测试复现，探针 test_U07；使用默认 1.2 秒 debounce 和阻塞式 Fake 图片解析器。  
严重程度：P1。  
受影响用户及场景：联系人先发图片，再紧接“这是什么”；本地下载/转码耗时较长。  
前置条件：图片解析超过 debounce 窗口；文本已到达。  
最短复现步骤：投递图片并暂停解析 → 投递“这是什么”并等待处理 → 完成图片解析。  
实际结果：保存的 user 顺序为“这是什么”→“[图片]”；模型调用 2 次、Fake 回复 2 次。  
预期结果及依据：现有连续消息与图片上下文约定，应保留事件先后和关联关系；技术处理完成顺序不等于用户发送顺序。  
用户影响：机器人先猜一个答案，再对迟到的图片另回一句，用户误以为视觉识别不稳定。  
证据或相关文件位置：[图片解析在入队和版本更新之前](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:337)、[事件并发处理](C:/Users/24028/Documents/chatbot/app/adapters/qq.py:225)。  
建议改进方向：先记录到达与排序，再异步解析；同会话等待必要图片或有明确文本降级；防止早到事件在解析完成后变成“新消息”。  
验收标准：同会话历史不因解析速度反转；图片与紧邻问题仍保持关联；不同会话不被慢图片阻塞。

### U08：切换联系人后，上一位联系人的草稿留在新会话输入框

问题性质：交互缺陷。  
证据状态：测试复现，探针 test_U08；调用实际选择和发送回调。  
严重程度：P2。  
受影响用户及场景：同时与多位联系人交流，输入后暂不发送。

预期结果及依据：体验判断：会话草稿应归属该会话；切换目标不能默默搬运未发送内容。README 没有承诺草稿功能，因此不把未实现草稿持久化本身判为 Bug。  
用户影响：容易把不适合 B 的内容误发给 B，或需要客户每次手动清空。  
证据或相关文件位置：[选择会话未处理输入框](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:761)、[发送使用当前目标](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:1181)。  
建议改进方向：按账号+会话保存草稿；或明确清空提示/转移确认；同时显示当前接收者。  
验收标准：A→B→A 时草稿归属明确；B 默认不会继承 A 草稿；后台历史刷新不改变草稿。

### U09：人工发送失败后，输入已清空，无法直接恢复或重试

问题性质：交互缺陷。  
证据状态：测试复现，探针 test_U09；真实发送回调、Fake 失败 Sender。  
严重程度：P2。  
受影响用户及场景：人工发送较长文字时遇到断线或发送错误。  
前置条件：输入框有文字，Sender 返回错误。  
最短复现步骤：输入合成文字 → 点击发送 → Fake Sender 失败。  
实际结果：提交时立即清空输入；虽然有 send_error 事件，但没有输入恢复或失败气泡承载正文。  
预期结果及依据：体验判断：操作失败应能从已有输入恢复，不能让客户重打一遍。  
用户影响：内容丢失、重复劳动；客户无法判断需重发还是等待。  
证据或相关文件位置：[未确认成功即清空](C:/Users/24028/Documents/chatbot/app/ui/desktop.py:1187)、[错误只携带异常](C:/Users/24028/Documents/chatbot/app/ui/runtime.py:540)。  
建议改进方向：保留待发送正文与目标；用失败气泡和重试/复制入口处理；不要覆盖用户随后输入的新草稿。  
验收标准：失败文字和接收者可恢复；重试不产生重复发送；等待成功期间可以继续起草新内容。

### U10：模型超时等错误只进日志，桌面客户只看到消息而没有回复

问题性质：交互缺陷。  
证据状态：测试复现，探针 test_U10；Fake 模型超时后捕获 DesktopRuntime 事件队列。  
严重程度：P1。  
受影响用户及场景：首次使用真实 Provider、API Key 错误、模型超时或服务异常。  
前置条件：QQ 入站成功，但聊天模型抛 ModelError。  
最短复现步骤：投递一条合成私聊 → Fake 模型抛超时 → 检查桌面事件。  
实际结果：队列仅有入站 message，没有模型错误或失败状态事件；GUI 使用的 sink 将提示写入日志。  
预期结果及依据：首次交流任务需要可见的生成/失败状态和恢复入口；错误不能让客户猜测是没收到、没登录还是模型没响应。  
用户影响：核心交流失败但原因不可见，客户只能重连、重复发消息或求助开发人员。
